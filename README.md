# Plateway

Design train layouts for standard brick track that mix the track you own with 3D-printed pieces: **Build track → Test drive → Print**. The app prepares labelled plates for your slicer — plain 3MFs that open in any slicer, STLs, and for Bambu printers Bambu Studio projects with painted supports and their G-code; it never starts a printer, and only running your real train proves a layout works.

Live at <https://plateway.alexcarvalho.me>. This repository is the published source: it receives one snapshot per released version, under AGPL-3.0. To send feedback or report a bug, use **Feedback** in the app or on the site; community pieces, trains and furniture go through **Contribute** into [the community library](https://github.com/AlexMC/plateway-library).

## Run locally

Requires Node.js, Python 3.11–3.13, [uv](https://docs.astral.sh/uv/), and **Bambu Studio at `/Applications/BambuStudio.app`** with X1 Carbon or A1 mini profiles installed. Elsewhere, set `BAMBU_STUDIO_CLI` to the executable (on Linux, the extracted AppImage's `squashfs-root/AppRun`); its bundled `resources/profiles/BBL` supplies the presets. The export service uses its real local CLI to check every plate and slice the Bambu projects; missing executables/profiles and slicer warnings fail the export rather than producing a pretend slice. The plain 3MFs and STLs it writes open in any slicer. Plate previews are drawn by the service itself from the plate meshes.

```sh
npm ci
uv sync --frozen
npm run build
uv run python -m cad.service.app
```

Open `http://127.0.0.1:8765/` (or `http://localhost:8765/`) for the landing site and `http://127.0.0.1:8765/app/` for the app: the app is built with Vite `base: '/app/'`, and the API stays at `/api/`. For development, run `npm run dev` separately and open `http://127.0.0.1:5173/app/`; its `/api` proxy targets port 8765. Set `TRAIN_ALLOWED_ORIGIN` to the Vite origin when using that server. The service accepts these two loopback names only at the configured host/origin ports; other hosts, schemes and ports remain rejected. Every unsafe `/api` request needs an allowed Origin, and a request carrying a session cookie also needs that session's CSRF token in `X-Workshop-Session`. Every response carries a Content-Security-Policy with no inline script (`site/js/landing.js` holds the landing page's script), plus `nosniff`, `X-Frame-Options: DENY` and, on https, HSTS.

`deploy/Dockerfile` builds the service for linux/amd64 with the pinned, sha256-checked Bambu Studio AppImage (the version `cad/tests/fixtures/coupon-slice-reference.json` records), the built app and the landing site: `docker build --platform linux/amd64 -f deploy/Dockerfile -t plateway .`

### Hosted

Hosted, `python -m cad.service.app` reads `PLATEWAY_PUBLIC_ORIGIN` (for example `https://plateway.alexcarvalho.me`): the expected host and allowed origin come from it, there is no local member (`/api/session` is gone), the prepare worker is its own process (`python -m cad.service.worker`), and the client IP for rate limits is Cloudflare's `CF-Connecting-IP`, never `X-Forwarded-For`. `PLATEWAY_BIND_HOST` (default `127.0.0.1`) and `PLATEWAY_PORT` (default `8765`) set where it listens. `PLATEWAY_LIBRARY_URL` names the public library host, which the Content-Security-Policy allows together with the S3 endpoint's host. An admin sees the R24 upsize trigger (the 7-day p95 queue wait) at `/admin/ops` (`/api/admin/ops` as JSON); everyone else gets a 404. `deploy/compose.yml` runs `api`, `worker`, `litestream` and `cloudflared` on Plateway's own server. The operations runbook (`docs/operations.md`: setup, deploy, backup restore, the triggers, moving to another server) names the server and accounts, so it is not in this public mirror; mentions of it here and in comments refer to that private file. Local staging runs with MinIO (`deploy/compose.local.yml`).

### Prepare jobs

Preparing plates, a calibration coupon or a grade rig is a queued job (`cad/service/jobs.py`): `POST /api/jobs` with `{"kind": "layout", "manifest": …}` or `{"kind": "coupon" | "grade", "parts": …, "printer": …}` returns the job (202), or the member's job already queued or running (200); the app polls `GET /api/jobs/<id>` every 3 s for its state, queue position, stage (`cad`, `arrange`, `slice`, `guide`), step and progress, and `DELETE /api/jobs/<id>` cancels it. `GET /api/jobs` returns the member's active job, whichever project or kind (with the saved project it prepares, so another project's Print step can name it and link to it), and each daily limit's prepares left with `resetsAt`, when the next one frees up (a 429 carries the same `resetsAt`). The Print step resumes that job on load and shows its queue position, stage, progress and **Cancel**; a layout prepared in parts shows "Part 2 of 3" with that part's stage, and a refused layout shows the limit beside its piece's numbers. A worker (`cad/service/worker.py`) runs one job at a time, each in a fresh `python -m cad.service.prepare_job` process in its own session; a cancel or the 90-minute timeout ends that process with its slicer. `uv run python -m cad.service.app` runs a worker in the same process; hosted, `python -m cad.service.worker` runs it alone, on the same `TRAIN_PROJECT_DIR`, `PLATEWAY_DB` and `TRAIN_EXPORT_DIR`. A member may prepare 10 layouts and 20 coupons or grade rigs in any 24 hours; system failures do not count. Before queueing, the service estimates a prepare's peak memory from its printed parts and distinct CAD builds (calibration in `jobs.py`); a layout above the 6 GB per-part limit is prepared in parts split at track joints between pieces (`cad/service/split.py`), and only a layout with a single piece above the limit is refused, with the numbers.

A layout prepared in parts comes back as one package (`cad/service/combine.py`): plate numbers run on across the parts, every part's plates, Bambu projects, G-code and STLs are in it, and one PDF guide with one shopping list covers the whole layout and lists which plates and pieces each part held.

Prepared files are kept for 7 days (`cad/service/storage.py`, `cad/service/receipts.py`). A finished package is uploaded to the private `plateway-packages` bucket under `packages/<member>/<package>/`, its receipt is stored in SQLite and the local build folder is removed. The bucket's lifecycle rule deletes the files after 7 days; the receipt stays, so `GET /api/packages` and `GET /api/packages/<id>` still list it with `"expired": true` (and the job reads `expired`), downloads answer 410, and `POST /api/packages/<id>/prepare` queues the same prepare again. Only the owner sees a package: anyone else gets 404. A single file (`/api/packages/<id>/files/…`) redirects to a presigned link valid for 15 minutes; the guide PDF and the ZIPs stream from storage through the service. Calibration results are each member's own, in SQLite, bound to the digest of the sample's receipt, so a result can still be recorded after the sample's files expired.

Hosted, set `PLATEWAY_S3_ENDPOINT` (the R2 account endpoint), `PLATEWAY_S3_ACCESS_KEY_ID` and `PLATEWAY_S3_SECRET_ACCESS_KEY` (`PLATEWAY_S3_REGION` defaults to `auto`); `PLATEWAY_PACKAGES_BUCKET`, `PLATEWAY_LIBRARY_BUCKET` and `PLATEWAY_BACKUPS_BUCKET` rename the three buckets. `plateway-packages` must have one rule deleting objects after 7 days and `plateway-library` no expiry rule; R2's bucket-scoped tokens cannot read lifecycle rules, so the service does not, and each deploy checks them first with `uv run python -m cad.service.storage check-r2` (wrangler, `docs/operations.md`). Without an endpoint, each bucket is a folder under `PLATEWAY_STORAGE_DIR` (default `storage/` in the project directory), which applies the same 7-day rule whenever it is opened; the service itself serves its presigned links at `/api/storage/…`. The worker needs the same settings.

### Community library

The app loads the approved community library before it opens any layout (`src/domain/library.ts`): `GET /api/library/index.json` serves `index.json` from the `plateway-library` bucket and the files it names beside it. Locally, that is the folder `$PLATEWAY_STORAGE_DIR/plateway-library/objects/`; hosted, the service redirects to `PLATEWAY_LIBRARY_URL`. To try the sample library (a 90° curve, a locomotive, a plain table and a removed item), copy `tests/fixtures/library/` into that folder. Pieces join a Community group in the palette that says they print as uploaded, trains join Test drive's train picker and furniture joins the Furniture group, each with its credit. If the index doesn't load, the built-in catalogue works as before; a layout that uses a community piece then shows it as an unavailable placeholder, which Checks lists and Prepare refuses until the page is reloaded or the piece replaced.

Layouts with community pieces prepare like any other. The manifest names each community piece by library id, version and digest (`library`); the prepare reads the item's entry and STL from the library bucket (locally the folder above; hosted, over `PLATEWAY_LIBRARY_URL`, so the worker holds no library token) and refuses a file whose sha256 differs. The piece is never regenerated: its STL goes onto the plate byte for byte, connector supports are painted where it overhangs at its marked ends, and the receipt notes that print style and fit adjustment don't apply. A retired item still prints; a removed one is refused. The guide's last page credits every community piece with its maker and licence, across all parts of a layout prepared in parts.

`index.json` is `{"format": 1, "items": [...]}`. Every item has an `id` (`community_` plus lowercase letters, digits and `_`), a whole `version`, a `kind` (`piece`, `train` or `furniture`) and a `state`: `live`, `retired` (left out of the palette and picker, but layouts that use it still open, show and fit it) or `removed` (a tombstone: its files are gone and layouts that use it show the placeholder). A live or retired item also has a `name`, a `licence`, a `credit` (the contributor's display name when it was approved, then ", adapted from" and the source's authors for an item adapted from another CC BY model), one `file` (a path relative to `index.json`, inside its folder) and that file's lowercase hex sha256 `digest`; the app checks train and furniture files against it when loading. It registers a piece from its entry alone and downloads its STL the first time a placed piece is drawn (once per digest): Build's 3D view and Test drive then draw the uploaded mesh with its marked ends on the route's ends, and the top view draws its plan silhouette under the track. An STL that fails to download or differs from the digest leaves generic track and a quiet note. A prepare checks a piece's STL against the digest too. A train's car is referenced by id and digest only (`library:<id>@<sha256>`), never by URL.

- `piece`: `file` is a binary STL in mm, +z up, its flat underside at z = 0. `piece.ends` are its two marked ends, `{"x", "y", "z", "heading"}` each: the track centreline where it crosses the end face, at rail-top height, and the direction (radians, anticlockwise from +x) pointing out of the piece through that end. The ends must be level (within 0.5 mm), at least 16 mm apart and face away from each other, turning at most 90°. The piece's track runs from the first end to the second, along a circular arc when one joins them and a smooth cubic otherwise (`src/domain/pieces/families/community.ts`). A piece adapted from another CC BY model (Plateway's own track adapts lev's rerailer, say) also has `piece.source`, `{"url", "authors"}`; its licence stays CC BY 4.0.
- `train`: `file` is one car's glTF binary in the car frame (`src/domain/trains.ts`); `train` holds `year`, `power`, `gauge` (`standard` or `monorail`) and `car`: `kind`, `motorised`, `length`, `width`, `height`, `wheelbase`, `bogies`, `couplers` (`front` > 0 > `rear`), a plan `outline` of 3 to 40 points and `triangles`; a model adapted from another CC BY model also has `train.source`, `{"url", "authors"}`, and keeps that model's licence.
- `furniture`: `file` is a `FurnitureType` JSON (`src/domain/furniture.ts`) whose `family` is the item's `id`.

#### Contributing

Verified members contribute through **Contribute** (the Gallery dialog, the start screen, or `/app/#contribute`), up to 5 uploads a day, and 5 tries an hour or 15 a day counting refused ones; admins have no limit (`cad/service/submissions.py`, `src/contribute/`). Every form shows that an approved upload and the contributor's display name are public on GitHub permanently, then asks for the rights attestation: CC BY 4.0, or for a train model adapted from another CC BY model (LDraw, say) that model's licence with its source address and authors. A piece adapted from another CC BY model stays CC BY 4.0 and names that model in its upload's `metadata.source`, `{"url", "authors"}`, as a train does (through `POST /api/submissions`; the piece form has no source fields).

- **Piece**: binary STL only, up to 20 MB and 200,000 triangles, in millimetres, at most 166 × 166 mm in plan and 180 mm high (it prints as uploaded, and the A1 mini's arrange keeps a 7 mm margin round its 180 mm bed); contributed pieces are two-ended plain track for now. In the mark-the-ends editor each click on an end face places the next end, snapped to the connector grid: the middle of that face (everything in its plane facing out, taken together, since a connector's tongue and socket split it; at least 16 mm across), at rail height (the highest point within 32 mm), heading straight out of the face as an arrow that **Flip arrow** turns round; **Clear** removes one end, and once both are marked the centreline between them is drawn.
- **Train**: one self-contained glTF binary in the car frame, as `scripts/trains/glb.py` writes it: one embedded buffer, vertex colours, no external URIs, images, textures or extensions, up to 250 KB and 12,000 triangles across every mesh and primitive. The member enters the set facts, bogie pivots and coupler faces; the service measures the length, width, height, outline and triangles from the model.
- **Furniture**: a form for the outline, the surfaces track runs on with their heights, an optional cubby grid (rows, columns, opening), colour and label, previewed live in the Build 3D scene; it sends the `FurnitureType` JSON, and a cubby grid larger than the outline is refused.

`cad/library/check.py` runs every check, in the app before the quick look and, standalone (`python check.py piece|train|furniture FILE METADATA.json`), in the library repository's pull-request workflow; it imports only the standard library, numpy, trimesh and manifold3d. An upload that fails is refused with the reason (holes, the wrong unit, an end off the end face…) and not stored. One that passes waits for Alex's quick look (`/app/#review`; a 404 for everyone else), and every admin gets an email. **Reject** needs a reason, which the contributor sees under **Your uploads** next to "Rejected" with **Submit a corrected version** (the form filled in again with that upload's metadata); a rejected upload never reaches GitHub. **Approve** hands it to the library bot (`cad/service/github_app.py`), which commits it to the public library repository (`library-repo/` here; files under `pieces|trains|furniture/<id>/1/` with its `metadata.json`) on a `submissions/<id>` branch and opens one pull request, crediting the contributor by display name only; the repository's `check` workflow runs the same `check.py`. Every 5 minutes the bot polls the open submission pull requests (ETag conditional requests; no webhook). A merge copies the file into `plateway-library` and adds the item to `index.json` with its credit and digest (`cad/service/library_publish.py`), so it joins everyone's palette; the contributor sees "In the library". A pull request closed without merging shows as "Rejected" with the closing comment as the reason, and rejecting an open pull request in the quick look has the bot close it with Alex's reason. A merged item later reverted is retired. From the quick look of a published item Alex can **Retire** it (out of the palette; layouts that use it keep it) or **Remove** it for a takedown (a tombstone in the index; its files leave the bucket and the repository's current tree). Deleting an account withdraws its uploads that are not yet merged, and the bot closes their pull requests. The bot runs in the API process when `PLATEWAY_GITHUB_APP_ID`, `PLATEWAY_GITHUB_APP_PRIVATE_KEY` and `PLATEWAY_GITHUB_REPO` are set (docs/operations.md, "Library repository and GitHub App"); without them approved uploads wait. `tests/fake_github.py` is a stand-in for GitHub's API for tests and local runs.

### Accounts

Projects, calibrations, packages and AI planning need a signed-in member; preparing plates and AI planning also need a verified email. The shopping list and print presets work without an account. `/api/auth/*` covers sign-up, email verification, sign-in, sign-out, `me` (the member, with the `purgeAt` deletion date while unverified, and their CSRF token) and password reset; `/api/account/*` covers the display name, password and email changes, a ZIP export and deletion. Passwords are argon2id hashes; sessions live in SQLite (`plateway.db`) as sha256 hashes behind an `HttpOnly`, `SameSite=Lax` cookie, named `__Host-plateway` (and `Secure`) on an https origin and `plateway` on plain-http loopback. Brute-force limits are documented at the top of `cad/service/accounts.py`.

Account email goes to a file sink by default: one JSON file per message in `PLATEWAY_MAIL_DIR`, or `mail/` inside the project directory. Verification and reset links point to `/app/#verify=…` and `/app/#reset=…`. For real delivery through Cloudflare Email Sending, set `PLATEWAY_MAILER=cloudflare`, `CLOUDFLARE_EMAIL_TOKEN` (an account API token with the Email Sending send permission), `CLOUDFLARE_ACCOUNT_ID` and `PLATEWAY_MAIL_FROM`; `PLATEWAY_MAIL_FROM_NAME` (default `Plateway`) is optional.

The app works signed out: visitors design, run Checks and test drive, and the draft stays in the browser. **Save**, **Open**, preparing plates and calibrations ask for an account: **Sign in** in the header, or the sign-up form those actions open, keeps the current work. A member's name in the header opens their account: display name, **Export my data**, **Sign out** (which asks *Save before signing out?* when there are unsaved changes, then starts fresh, because the service clears the browser's stored data) and deletion (current password plus the display name to confirm). An unverified member sees a banner with **Resend** and the date the account is deleted unless verified. Locally the verification email is a JSON file in `.projects/mail/`; open its `/app/#verify=…` link (the service serves the app at `/app/` as well as `/`). The tab rechecks the account whenever it regains focus, so verifying in another tab shows at once. Every browser call goes through `src/net/api.ts`, which sends the cookie, adds the CSRF token to unsafe requests and turns a 401 into "Signed out — sign in again" without touching the draft.

A member's projects live on the service under their account (SQLite, `cad/service/projects.py`); **Open** lists only their own, and every **Save** adds a revision. The service mints project and revision ids, and a save names the revision it started from: when another tab or device saved the project since, the save is refused and the app asks *Newer save exists* — **Keep both** saves the changes as a new project, **Use newer** opens the newer save. Opening an older save and saving it makes it the newest. Signing up or signing in saves a visitor's edited browser draft to that account once (signing in again, or from another tab, does not copy it); an untouched new project is not saved, and a draft from another account is never saved into this one (its unsaved work is kept aside). A browser draft that cannot be read starts a new project and is kept in `localStorage` under `train-layout-workshop:current:recovered`. A piece the library no longer has opens as an *Unavailable piece* along its saved footprint, keeps everything it saved, and blocks preparing plates until replaced.

The browser app never uses `GET /api/session`. `uv run python -m cad.service.app` keeps it as a development-only bridge for local scripts: it signs the caller in as one verified local member (`local@plateway.invalid`) and returns its CSRF token, so `scripts/plan.ts --save` needs no email round trip. `create_app` serves it only with `local_member=True` and refuses that on a non-loopback host.

## Workflow

The header's three steps are tabs: click one, or focus it and use ←/→, Home and End. Build's **Go to Print** skips Test drive (still recommended); each later step has a **←** button back to the one before.

The app opens on Build track. A new project starts with a typical starter set's track (8 straights, 16 R40 curves), an example train (the 60052 Cargo Train), a 2400 × 2100 mm table and the X1 Carbon printer.

A project with no track opens Build on a start screen with three ways in: **Describe it** (type what you want and Generate — it opens Describe track with your words and starts it, after asking for an Anthropic key if this browser has none), **Start from an example** (the plans in `docs/plans/examples`, each with a thumbnail and its track length, owned and printed piece counts and whether it fits your room and inventory — one that needs a bigger room is still pickable; picking one lays it as one undoable change) and **Build by hand** (or Esc: opens the palette search). Pieces and the build summary stay usable around it. It leaves as soon as the table has track and stays away for that project once you choose Build by hand; a new project shows it again.

1. **Build track:** place owned or printed pieces in top or 3D view — the seven standard shapes (straight, R40 curve, flex, left/right turnout, 90° crossing, double crossover) plus printed straights of any length, curves from R24 to R184, S-bends, easements, ramps and bridge decks. The Pieces sidebar is one list: **Your track** stays pinned at the top with a small tile for each track family you own (straights, R40 curves, owned turnouts, crossings, flex) and how many are left — the same tiles as in the list — or, if you own none, a link to set them in Setup. Below it each group (Track, Junctions, Elevation, Mechanisms, Scenic, Experimental, Furniture) has a header that sticks to the top while the list scrolls, shows its count and folds or unfolds on click; this browser remembers which are open (Track and Furniture at first). The chips under the search jump to a group, unfolding it. Search by name, size or family looks through every group, folded or not, and folding comes back when the search is cleared. The piece you are working with opens in one **piece panel** beside the Pieces sidebar (a bottom sheet on phones, with the placement bar just above it): click a tile and it shows **Placing:** that tile; select a placed piece (or shelf) and it shows **Selected:** that piece; when you arm a tile with a piece selected, Placing wins. Both use the same sections in the same order — **Shape** (size chips, parameters, flex bend, ramp height), **Print** (Own / Print / Fast and how many owned are left), **Also needs**, **Settings** (turnout routing and other states) and **Info** — and for a selected piece a folded **Route height** (the floor its whole route sits on) and its **Flip**, **Rotate route** and **Delete**. Click the table to place an armed piece repeatedly, or drag the tile to place it once; Esc, × or deselecting closes the panel, and its edits to a selected piece are each one undoable edit. Pieces snap to each other's ends (only ports of a compatible gauge mate). **Close gap** (toolbar, then click two open ends; or **Close this gap** in Checks when two level ends face each other within 400 mm) lists up to three ways to join them, owned stock first and the one with least to print preselected: spare owned R40 curves for a turn of whole 22.5° steps and spare owned 128 mm straights along what is then in line, with a made-to-measure printed piece for the rest ("2 owned straights (256 mm) + 80 mm printed"), and the made-to-measure piece alone ("1 printed straight 336 mm") — a straight, one curve with a straight, or an S-bend. Each way is laid on a copy and offered only when it closes exactly; **Place** lays the chosen one as one undoable change, joining the routes or closing the loop. **Tightest bend allowed** (R320 by default, down to R192) shows only when it matters — when a made-to-measure piece bends, or nothing joins the ends at the current limit. Size and angle chips that build a piece you own say how many are left ("R40 · 16 owned", or "none left"). The Furniture group's KALLAX 5×5 tile adds a shelf — click it, then the table (R turns it), or drag it on; click a placed shelf to move, turn or delete it. The **−/+/⤢/?** cluster (bottom-right) zooms and fits the layout, as do the toolbar buttons and the scroll wheel; fits, check framing and the zoom buttons ease over about a third of a second, the first piece frames at least an oval's worth of room (and any shelf), and as a chain grows towards the edge the view pans, or zooms out to keep the layout in sight (after you zoom by hand it only pans, unless the end leaves the view). While a piece snaps onto a chain end, and for a selected chain end, a label shows how far round the chain has turned ("135° left of a loop"), when the end is parallel to the start (a faint guide runs along the start direction), and when one more piece closes the loop. The canvas toolbar keeps the same groups whatever you do — **View** (Top / 3D), **Navigate** (Zoom in, Zoom out, Fit track, Fit room, Pan), **Tools** (Describe track, Close gap) and **History** (Undo) — each an icon with a short label (icons only below 1280 px wide). What the armed piece or the selection can do is on the **placement bar**, fixed at the bottom centre of the canvas: while a tile is armed it says what you are placing and offers rotate 22.5° either way (R / ⇧R), **Flip** (F: a curve turns the other way — **Curve left/right**, **Shift left/right** for an S-bend — a turnout swaps hand — **Swap hand** — a ramp climbs the other way — **Ramp up/down**), **Other side** (Tab, when there is more than one way: which way round the piece faces where it joins, e.g. a turnout entered from its points, its straight road or its branch) and **Done** (Esc); for a selected piece rotate (disabled, with the reason, when it is joined at both ends), **Flip**, **Rotate route** (turns the whole connected track), **Options…** (moves the keyboard into the piece panel) and **Delete** (Del); for a KALLAX, armed or selected, **Rotate 90°** and Done or Delete. Each button shows its key. A snapped ghost shows arrows from the joint along the way(s) it goes. With the pointer on the bar (or off the table) the ghost stays put — back where the pointer last rested before heading for the bar, so it keeps the open end it had snapped to — and keeps answering the bar, R, F and Tab; back on the table it follows the pointer again. Press **?** (or the **?** under the zoom buttons) for **Keyboard shortcuts**, every key and gesture in Build; the first time you place a piece a tip names the main keys until you dismiss it or finish placing. R turns a selected piece on its own about the joint holding it (a chain's end piece leaves the chain and rejoins when turned back); a piece joined at both ends can't turn alone — Flip mirrors it in place, Route turns the whole track. Drop a piece onto placed track (away from an open end) to put it into that route at the nearer joint, main line along the route: when a run of whole pieces from there ends exactly where the new piece ends (a 256 mm turnout over two 128 mm straights) it replaces them and owned ones go back to stock; otherwise the rest of the route moves along, with anything branching off it, and a closed loop opens on its far side — the preview shows the gap and, once placed, **Close gap** is offered. Near an open end or a joint the ghost locks to it and stays while the pointer moves about it (it lets go about 40 px beyond the snap circle, or on Esc); the other ways the piece fits there — both hands, facing along or against the track, at most six — show as faint dashed outlines (hover one for its name), and the one whose branch (or far end) points towards the pointer is the ghost: point where you want it to go and click. F and Tab step through the same ways; what they (or the last piece laid) chose — branch outside or inside the loop, or to the left or right of travel, facing along or against it — carries over to the next joint until you point somewhere else. A turnout can go in facing against a route that already has one: it joins the route at both ends as its own short route. Where the chosen way would push track along or open a gap, the ghost moves to the nearest joint up to three along the route where it fits cleanly (the hint says so: "fits cleanly 1 joint left"); only when none does is the gap shown. A junction or mechanism that fits no run of whole pieces (a 336 mm turntable on 128 mm straights) instead replaces the fewest straights longer than it and makes up the difference with a printed straight spacer, at least 24 mm — "Replaces 3 straights (3 back to stock) + a 48 mm printed spacer · nothing moves", said beside the ghost too; Tab still offers moving the track on, with its gap. Printed track is plastic — it won't carry metal-rail 9 V power.
2. **Test drive:** run your train over each route to check the path, clearance and ramps. Train-set cars are drawn from their LDraw models (custom cars as a simple car from their sizes); each body rides its bogie pivots and couples face to face across curves. Preview only — run your real train after printing.
3. **Print:** opens with **Ready to print?** — the printer, print style, pieces to print, plates prepared and whether the layout has been test-driven. Check the **Shopping list** (everything to buy besides the printed parts), prepare plates for the printed pieces, download them and open them in your slicer. **Download all** holds a plain 3MF per plate (opens in OrcaSlicer, PrusaSlicer, Cura or Bambu Studio; turn on supports for the connector ends — see the guide), the STL files and the assembly guide, plus a `bambu-studio-<printer>` folder with each plate's Bambu Studio project (supports painted only where needed) and G-code for Bambu printers. Each plate also downloads on its own. Optional connector calibration, a grade rig for ramps, and simple after-you-print checks live here too. **Advanced** holds the printer, material, process, nozzle and part-size settings, the parts list and all generated files.

**Setup** opens as a side panel from the header, or from the count of track you own in Build, "Add your train" in Test drive and the measurement links in Print. It holds the track you own (with a Typical starter set or None preset), your train — pick standard-gauge and monorail train sets (public/trains, built by scripts/trains; credits under Setup → About these models) by number, name or power and add a whole set or single cars, measured from the LDraw model, or enter custom cars (the example train stays until you add your own), table size and ramp space, and the printer. Values you type are used as your measurements; muted defaults are not. Click the project name in the header to rename it.

Owning fewer pieces than the layout uses is a warning, never a blocker: owned pieces are never swapped for printed ones unless you choose to. Overpasses need your real cars in Setup so the bridge clearance can be checked. Legacy custom-joiner projects need their measured rail dimensions.

**Checks** in Build's sidebar lists errors, warnings and info, one row per problem: the same problem on several pieces is one row ("On 120 pieces"), the steepest ramp and its grade advice are one row, and a crossing shows its measured clearance against your tallest car (or says what is missing: your cars in Setup, or a Bridge piece over it). Click a row (or Tab to it and press Enter; ↑/↓ move between rows) to frame and outline what it is about in the top or 3D view — its pieces, supports and points; click it again, press Esc or select a piece to clear it. Where one reliable change fixes it, the row offers it as one undoable edit: **Switch extras to printed** for owned pieces beyond your inventory, **Raise helix to … mm per turn** when helix turns are too close (the least rise per turn, within the 5% grade, that clears it; a closed loop's helices are raised together), **Close this gap** for open ends and **Add cars in Setup** for an unchecked crossing. A route that runs nearly round a loop without closing is a **Loop doesn't close** warning that says why in plain words ("The loop is 1 curve piece short (22.5°): the left bend has 7 R40 curves, the right bend 8. The top side is 1 straight (128 mm) shorter than the bottom side.", or that the ends are offset sideways); selecting it outlines both ends and the side where the pieces belong. When whole pieces close the loop exactly it offers them first — **Add 1 × 128 mm straight on the top side and 1 curve piece**, owned stock first, then printed, as the row notes — laid with the insert logic, so the track after that side moves along; **Close this gap** (a made-to-measure printed piece) follows whenever one can join the two ends. Dead ends and sidings stay plain open ends. Every fix (and Close this gap) is first tried on a copy of the layout: an error it would add is said under its button before you click ("Then track leaves the room, 102 mm past the wall at x = 0.", "Then track runs into K1.") and the fix is still offered; a fix that would add an error of the same kind as the one it clears is not offered. **Track leaves the room** is an error for any piece or support past the room's walls (Setup's size, or the default 2400 × 2100 mm), worded as the plan builder words it, with **Set the room size in Setup**; **Track runs into K1** is an error for track through a KALLAX's panels (track resting on a cubby floor is fine). Both are the same check the plan builder runs, and neither blocks export.

## Track styles

Each printed brick-track piece is made in one of two styles, chosen in **Build**: **New prints: Full detail | Fast** at the top of the palette sets the style for every tile (owned track still comes first while you have some left; switching it resets per-piece Print/Fast picks but keeps Own picks); a tile's options override it with **Own**, **Print** or **Fast** (printed-only pieces offer **Print** or **Fast**). Or select a placed piece and switch it under **Print** in the piece panel, which can also give every printed piece in that route the same style. Fast pieces are drawn lighter and yellower in Build and Test drive, without their inner ties and studs, and the Build summary counts detailed and fast pieces separately. Owned pieces, supports and brackets are never affected.

- **Print (full detail):** standard ties, studs and underside, so pieces sit on a baseplate. Prints with the process chosen under **Advanced**.
- **Fast print:** keeps the same connector ends (end ties and their studs), both rails, solid supports under each rail and thin braces between them — about half the print time and roughly a third less plastic. Pieces don't sit on a baseplate. Their plates print at the printer's largest standard layer height up to 0.28 mm (0.28mm Extra Draft for a 0.4 mm nozzle); turnout selectors, keepers and lock pins, and supports, keep the chosen process on their own plates. Plates never mix the two styles, and the printer card in **Print** lists the process for each style in use.

Changing a piece's style changes the printed parts, so prepare plates again; earlier files stay as they were.

## Connector calibration

In **Print → Connector calibration**:

1. **Generate calibration sample**, download its 3MF and open it in your slicer with supports on for the connector ends — or, on a Bambu printer, its Bambu project, whose supports are already painted.
2. Print it, remove the supports, then test both ends against your own track.
3. Tick **I printed and tested this myself** and choose **Too tight**, **Fits** or **Too loose**. The result is saved to the project and your local calibration library.
4. If needed, pick a looser or tighter **Fit adjustment** (−0.15 to +0.15 mm) and repeat.
5. In another project with the same printer settings, choose **Use this adjustment** under **Your saved results**.

Changing printer, material, process or nozzle turns the adjustment off until you apply or test one for the new settings. The calibration sample prints at the layer height of your printed track: fast when every printed piece is fast, full detail when none is; when a layout mixes both, **Test at** chooses (it starts on the style with more pieces), and each choice keeps its own adjustment. Full steps: [Connector calibration](docs/assembly/fit-coupon.md). Geometry details: [shared connector reference](docs/assembly/brick-end-trial.md).

## Crossings and gauntlet track

Fixed junctions: no moving parts, both routes always open, so only one train may use them at a time. Each is a Junctions tile with chips and **Custom**; left/right mirrors it.

| Tile | Chips | Custom |
| --- | --- | --- |
| Diamond crossing | 45° (20 × 20 studs, two printed parts); 22.5° R104 star (42 × 42 studs, three parts) | any angle from 15° to 90°, both legs 64–1024 mm |
| Curve crossing | R40 or R56 arc crossing a straight: 45° with a 45° arc (ends on the 22.5° curve grid), or 90° with a 22.5° arc | radius 192–1472 mm, crossing angle, arc angle, straight length |
| Gauntlet track | two tracks 16 or 8 studs apart squeeze to 16 or 8 mm apart and share one bed, rails interlaced | spacing 64–256 mm, offset 8–24 mm, entry and shared length |

Legs must be long enough that the other track's body clears the track joined at each port (at least 63.8 mm × cot(angle/2): 154 mm at 45°, 321 mm at 22.5°); the piece panel says how long. Below 22.5° a crossing is marked experimental. Every route's 2.2 mm flangeways are cut through the other routes' rails, which leaves the frog gaps; where a gap is longer than 4 mm, a check rail inside the opposite rail guides the wheelset across it. Where two routes' bodies overlap, a solid 3.2 mm studless crossing plate carries both, so the crossings sit on a flat table or clutch to bricks at their end ties, not on a baseplate. Pieces larger than the A1 mini's usable bed are split along straight seams between ties or through the plate, clear of frogs and check rails, and keyed with the same dovetails as the turnouts; no screws. `cad/models/crossing_any.py` builds and probes them (flange corridors, running-head gaps, wheelset guidance, source contacts, keyed joints).

## Turnouts

Printed turnouts with point blades, in the Junctions palette. Each has **Manual** or **Sprung** points, and its settings (2 or 3) show in a selected piece's panel and in Test drive's **Switches** list.

| Tile | Shapes | Settings |
| --- | --- | --- |
| Turnout (radius family) | R40 (the standard 53404/53407 shape, 32-stud main); R56 oblique (one R56 22.5° arc, then a straight so one more R56 curve lands 16 studs over; 40-stud main); R104 parallel over 80 studs and R148 parallel over 96 studs (Pythagorean S-bends ending 16 studs over) | Straight, Diverging |
| Curved turnout | R40 or R56, 45° or 90°: the inner route is the arc; the outer route starts with a straight so both exits end parallel, 16 studs apart | Outer, Inner |
| Wye turnout | both legs turn 22.5° on R40, then 32 mm straight | Left, Right |
| Three-way turnout | a left R40 (standard-shape) turnout, then a right one whose toe sits just past the left frog (55-stud main) | Straight, Left, Right |

The points are one printed part: two flexure blades joined by a tie bar, standing on a 1.4 mm floor in the base with 0.4 mm clearance all round. The blades bend between the tie bar and their heel blocks, which two keepers hold down (four M3 × 4 self-tapping screws per set of points). Push the knob on the tie bar to throw them (2.4 mm). **Manual** points print in the first setting; a small printed spacer dropped into the open blade's gap locks either setting. **Sprung** points print in the piece's current setting and spring back to it, so a train coming from the other route trails through (the wheels push the blades over): Test drive lets a train run a sprung turnout from the other route and blocks it at manual points set against it. Frog gaps are the other routes' 2.2 mm flangeways, with a check rail opposite any guiding-face gap over 4 mm (R148). Bases are split into keyed tiles that fit the A1 mini, along straight seams between ties; where two routes' bodies overlap, the first route's ties become long bearers that carry both, so seams cross the whole throat. The existing standard-shape printed turnouts keep their sliding selectors unchanged. `cad/models/turnout.py` builds any point-blade junction from a spec (ports, route centrelines, switches, settings) and probes it: points travel, keeper and stock-rail stops, spacer locks, operating envelopes, flange corridors and running-head gaps in every setting, keyed joints and source contacts.

**Servo drive.** Manual points can be set to **Drive: SG90 servo** in a selected turnout's panel (one servo per set of points; a three-way has two). The tie bar is raised over a printed throw rod that slides in from outside, pin first, through a window under the stock rail (the rail head bridges it) and runs square to the tie bar to a fork beside the track; an SG90 lies on its side in a printed housing there, its horn pin in the fork. A flat clamp screwed to the tie beside the window and to the housing's ledge (four M3 × 4) holds the housing to the track and roofs the rod. The servo sits away from the branch (right of a left-hand turnout and of a three-way, left of a wye), within 82 mm of the track — inside the 64 mm gap to a parallel track 16 studs away — and never past the toe; the editor reserves that zone, so track laid in it is flagged. The horn turns about ±8° either side of centre (2.4 mm throw plus 0.2 mm backlash); the servo holds either setting, so no spacer is used. Rod, housing and clamp print in the detailed style on every layout.

## Turntables, transfer tables and sector plates

Moving tables are in the Mechanisms palette. Their deck is one moving piece: each setting lines it up with one set of stub tracks, whose track connector ends never move, so you snap stall and lane tracks to any of them whatever the deck is set to. A selected table's panel and Test drive's **Mechanisms** list (◀ setting ▶) move the deck; a train runs across the lined-up tracks only, and a route that meets the deck set elsewhere ends there with the reason ("The turntable bridge is turned to Left 2.").

| Tile | Shapes | Settings |
| --- | --- | --- |
| Turntable | 32-, 48- or 64-stud bridge; stalls every 22.5°, 15° or 11.25° (up to 7/11/15 each side of the exit); pit ⌀ from 336 mm; by hand, Bluetooth L motor or Infrared L motor | One per bridge axis that meets a stall: In ↔ Out, Left 1, Right 2 ↔ Left 6 … |
| Transfer table | 32- or 48-stud deck; 2–6 lanes 16 studs apart, to the left or right | Lane 1 … Lane 6 |
| Sector plate | 48-, 64- or 80-stud deck pivoting at its entry; 2 or 3 fan tracks | Track 1 … Track 3 |

Stalls 15° apart need a 48-stud bridge and 11.25° a 64-stud one, so neighbouring stall rails keep 5 mm clear at the pit edge; the piece panel says so otherwise. The sector plate turns at most 5.625° at its pivot (a flex-track joint), so its far ends fan out off the stud grid — join them with Close gap.

Each table prints as keyed pit or well pieces (a 3 mm floor the deck slides on, stub tracks on standard 3.2 mm base) and a flat-bottomed deck split into keyed pieces, all within the A1 mini bed and printed without supports except at the connector ends. The deck's rails meet the stubs' across a 1 mm gap; 6 × 3 mm magnets in the floor and deck ends pull it into line and two 3 mm steel dowel pins lock it (worst-case rail-end error from pin and pivot play under 0.3 mm). The motorised turntable takes a cross axle through its pivot, driven from under the table by a Bluetooth L motor (88013) or an Infrared L motor (88003) through a worm gear and 24-tooth gear on a printed mount, which holds the worm's axle 16 mm (two modules) beside the vertical axle, square to it.

## Moving bridges and the train elevator

Also in the Mechanisms palette. Each runs straight from its `in` end: a 48 mm landing (track connector outside), the moving span, and another landing, so it stays on the stud grid (span in whole studs). The span's route is open only while it is in place; set it in its panel or Test drive's **Mechanisms** list, and a route that meets it raised, open or lifted out ends at the landing with the reason ("The bascule bridge is raised."). Both connector ends stay snap targets in every setting.

| Tile | Shapes | Settings |
| --- | --- | --- |
| Lift-out section | 8–20-stud span; lifts straight out (doorways, walkways) | In place, Lifted out |
| Hinged section | 8–20-stud drop-leaf hinged at its `in` end on two M3 screws | Down, Raised |
| Bascule bridge | 12–20-stud leaf on a cross-axle trunnion between two towers, bolt-on counterweights; by hand, Bluetooth L motor or Infrared L motor | Down, Raised |
| Swing bridge | 18- or 20-stud deck turning 90° on a centre pivot | Closed, Open |
| Lift bridge | 12–20-stud deck rising 64–128 mm between four posts; lifted by hand or by an M8 lead screw and crank | Down, Raised |

Every part fits the A1 mini bed and prints without support except under the landings' connector ends; decks, leaves and posts print in the detailed style even on a Fast layout. Seats are saddles over cone posts with 6 × 3 mm magnet pairs (hinged leaves are located by their hinge, so their posts carry no cone); the swing bridge's girders close against stop blocks with magnets in their faces; lift and elevator decks ride in shoes round the posts and are held level by M3 index pins. A hinged leaf's toe (hinged section, bascule) and its landing's end are arcs about the hinge, so the toe never runs into the landing as it rises. The elevator's posts carry its landings and car, so generic supports stay out from under it; level spacing must clear your tallest car (Test drive warns otherwise).

## Uncoupler track

The **Uncoupler track** (Mechanisms) is a 16-stud straight with a flap between the rails. **Lowered** (≤ 4.6 mm, under the tie-stud tops) trains pass; **Raised** it stands 19.55 mm tall (10 mm above the rail tops) across the gauge centre, clear of the flange corridors, and no train passes — Test drive's **Mechanisms** list sets it, and a route meeting it raised ends there ("Uncoupler raised — lower it to pass"). To part a train, stop with the coupling just past the flap, raise it and drive the loco on: the first wagon's leading bogie meets the flap and its magnetic coupling pulls apart (a physical trial for each wagon).

The flap turns on a printed D-shaft that runs under the near rail through solid stringers to a drive on the right of in → out, inside the 64 mm gap to a parallel track 16 studs away: **Magnet/manual** (an arm with 6 × 3 mm magnet detents in both positions, three magnets) or **Servo** (an SG90 in a printed cradle working the arm through a link and two 1.75 mm filament pins, horn about ±20°). Base, flap, rocker (and link) each print in one piece on the A1 mini bed; the base also prints fast.

## Narrow and dual gauge (experimental)

The Experimental palette group has narrow-gauge track — 24 mm (3-stud) gauge on 6-stud, 47.8 mm sleepers, after the 2009 brick narrow-gauge track and TrixBrix — and dual-gauge track, standard track with the narrow rails centred inside it (4 rails). Ports only mate a compatible gauge: standard and narrow ends never join directly (fit says "put dual-gauge track between them"), while dual ends join both.

| Tile | Shapes | Settings |
| --- | --- | --- |
| Narrow straight / curve / S-bend | any length; R24–R96 curves (22.5° by default, 45° is 85976's turn); S-bend 12 studs over 36 by default (two R30 arcs) | — |
| Dual-gauge straight / curve | any length; R40 and wider; level only | — |
| Gauge adapter | a 64 mm dual-gauge straight, offered as **Dual → narrow** or **Dual → standard**: lay it where standard track meets narrow track | — |
| Dual-gauge divergence | one fixed part: the standard route runs straight 152 mm (19 studs); the narrow route leaves on R24 through 45°, left or right, across the outer standard rail (frogs and four check rails) | none: Test drive sends each train the way its gauge goes |
| Narrow stub switch | a 24-stud deck pivoting at its entry swings its far end between two fixed narrow stubs 11.25° apart (a 5.625° kink at the pivot); by hand | Track 1, Track 2 |

Narrow point blades do not fit 24 mm gauge (their heel keepers need the routes 17 mm apart, which narrow routes reach only past the frog), so the narrow switch is a stub switch — the sector plate on the narrow profile. A route that meets its deck set to the other stub ends there ("The stub switch is set to track 1."); its far ends are off the stud grid, so join them with Close gap.

Set a car's **Track** in Setup to Standard (L-gauge), Narrow (3 studs) or Monorail. Test drive refuses a train on track that does not carry its gauge, and a route that runs on to track of another gauge stops there with the reason.

**Narrow connectors are this app's own.** A narrow end is the accepted standard end's central clip and pin with a plain outer half tie: it mates this app's narrow and dual ends only — not 85976 narrow track, TrixBrix or any other narrow track. How well the clip holds without the outer rail tongues, and whether wheels run cleanly through the divergence's frogs, are physical trials.

## Rotary dumper (experimental)

The **Rotary dumper** (Experimental) is a straight with a 16–20-stud cradle between two 6-stud landings that rolls one 6-wide wagon 150° about the track to empty it, by hand crank, a Bluetooth L motor (88013) or an Infrared L motor (88003). **Upright** its rails line up with the landings (0.6 mm gaps) and trains run through; **Tipped** a route meeting it ends at the landing ("The dumper is tipped."). Only 6-wide stock up to 80 mm over the rails fits through the cradle's side walls and rim ledges, which also hold the wagon at every angle.

The cradle's end rings (140 mm across, the barrel axis 72 mm up so the whole cradle clears the table) roll in grooves on four 608 bearings in the stands; a module-1 ring gear and a 16-tooth gear on a cross axle turn it, and a lug on the out ring lands on stop blocks with magnet detents at 0° and 150°. There is no pit, so the load drops onto the table under the cradle: clear it while tipped. The cradle and out ring print standing on end on the A1 mini bed without support; the landings with their stands print flat and also fast.

## Rack railway and cog bogie (experimental)

**Rack railway** (Experimental) is printed track with a rack between the rails, for grades up to 20 %. **Entry** eases from level onto the grade and its teeth rise over 48 mm. **Slope** holds the grade. **Exit** eases back to level. Entry and Exit are 1.6 m vertical curves by default, and the cog needs at least 1.28 m. The teeth have the brick gear-rack pitch (3743: 10 teeth per 32 mm, module 3.2/π). They stop 0.4 mm below the rail tops, so every train runs over the rack. Each piece has a whole number of teeth, so spacing stays continuous across joints and across the bed-sized parts fit splits it into.

Above 5 %, only a train with a cog car climbs: tick **Cog drive** on its loco in Setup, or Test drive refuses the route. The cog hangs 2.4 mm below the rail tops, so a cog train never runs through a turnout or crossing; Test drive refuses that too. Set **Cog bogies to print** on any rack piece to add a printed cog bogie (frame + 17-tooth cog) for your loco. It takes four 55423 train wheels on cross axles, and the cog axle is driven through a universal joint from a Bluetooth motor in the loco body.

## Monorail (experimental)

The **Monorail** pieces (Experimental) follow classic brick monorail geometry: a 4-stud (32 mm) beam, 12.8 mm tall. Pieces are straights 4–32 studs long, R224 curves of 30°, 45° and 90°, a two-part ramp (lower + upper, each 256 mm long and 48 mm up, 37.5 % at the steepest), and a 256 mm switch, left or right, that diverges 30°. They mate only other monorail pieces. A double-sided module-0.5 rack rod (163 teeth per side on 256 mm) runs in the groove for a classic brick monorail motor. A 2x4 brick plate under each joint clutches both ends. The groove, rod and switch dimensions are inferred from the original's published sizes and patent, so treat them as untested. Joining to original classic brick monorail track is also untested. Give monorail cars Track **Monorail** in Setup.

## Funicular (experimental)

The **Funicular** (Experimental) is a single steep line of 32–128 studs at 20–60 % (35 % by default). It never joins other track: both ends are buffers. Its car is hauled on a string by a winch drum on a Bluetooth L or M motor at the top station, so any standard-gauge car runs it in Test drive. Level printed straights lie on a bought plank. Printed wedge feet set the plank at the grade, the string runs over saddles on the middle ties, and a printed hitch clips the car's magnet coupler to the string.

## Automation devices

Prepared plates list every device a program can drive or read: servo-driven points, Bluetooth-motor mechanisms (a motorised turntable or bascule bridge), servo uncouplers and colour-marker sleepers. `manifest.json` (Layout data) carries them under `devices` — id, kind, piece, control, settings and position — and the assembly guide ends with the same table, each device also under its piece's or part's code. A marker's id is its insert's part id. Hand-worked pieces, and lead screws turned by a crank, are not listed.

## Shopping list and control gear

Every printed piece knows the bought parts it needs. Print's **Shopping list** adds them up for the whole layout as you build — no plates needed — grouped as fasteners, magnets, bearings & weights, brick parts, electronics and materials; each line opens to the pieces that need it, and **Copy list** / **Download CSV** take it away. The piece panel shows **Also needs** for that one piece (switching a turnout to a servo or a turntable to its motor updates it). Every piece that can be worked more than one way — turntable, bascule and lift bridges, train elevator, rotary dumper, uncoupler, the printed turnouts' servo, the funicular's motor — has its own **Drive** section in the piece panel, both while placing and once selected, with a line on what each choice takes (a Bluetooth hub, which an infrared train such as the 60052 can't drive; or an IR receiver and battery box), and its tile says "by hand or motor", including the control gear it adds (marked per servo, shared — up to 16 servos per driver board or 4 motors per hub — or once per layout); Print lists that gear under **Control gear**. The prepared assembly guide starts with the same list. Glue, graphite and mounting tape count once per layout; mounting screws come from the brackets' screw holes (two 4.5 × 30 mm wood screws per anchored bracket with the default 5 mm holes, 4 × 30 mm per wall bracket hole, 4 × 16 mm for shelf brackets) — pick wall plugs or anchors to suit your wall.

**Servos** (servo points, servo uncouplers) add one PCA9685 16-channel servo driver per 16 servos, an ESP32 (or any I²C microcontroller), a 5 V regulated supply of at least 2 A plus 0.5 A per servo beyond four (a 10 A supply above 16 servos) and an extension lead per servo. Each servo's two endpoints are trimmed in the controller's software.

**Bluetooth vs infrared.** Bluetooth motors (the turntable, bascule bridge and rotary dumper on **Bluetooth L motor (88013)**, the funicular, the cog bogie) add one Bluetooth 4-port hub (88012) per four motors (the Bluetooth train hub 88009 has two ports). Infrared sets such as the 60052 Cargo Train (88002 train motor, 8884 IR receiver, 88000 battery box) can't drive Bluetooth motors: the plugs and the protocol differ, so these need a Bluetooth hub. The turntable, bascule bridge and rotary dumper can instead take an **Infrared L motor (88003)**; those add one IR receiver 8884 and one battery box 88000 (or rechargeable 8878) per two motors — the 60052's own receiver and battery ride on the train, but its 8879 remote can drive the mechanisms' channel.

## Ramps, flyovers and risers

The Elevation group follows the community rules for brick trains: at most 5% (two plates of rise per 16-stud track; over 4% is flagged for long trains), grade changes eased over a vertical curve of at least 5.1 m (one plate per track), no turnout or crossing on a slope with at least 128 mm of level track before one, and 118 mm from the lower rail tops to the underside of anything crossing above.

Tiles run from Go up or down and the height kits (Helix, Flyover, Wall run) to single pieces (Bridge, Ramp set, Ramp piece · 8 mm, Helix section, Banked curve). Ramp set and Ramp piece · 8 mm stay as specialist pieces; projects laid with them open unchanged.

| Tile | What it lays |
| --- | --- |
| Ramp set | **Start** (eases from level onto the grade), **Slope** (constant grade) or **End** (eases back to level), at 2–5% up or down, straight or on any curve (R40–R88 chips or custom radius and angle). **Auto** length makes each easement one 5.1 m vertical curve (208 mm at 4%) and a slope one 16-stud track; any length can be typed. Each piece prints flat as a wedge with one flat underside and is split to the printer bed like any printed track. |
| Go up or down | The first Elevation tile (search finds it as raise, ramp, climb, up or down): **one piece** that climbs or descends from an open end to the height you set — type it (signed: below the table goes below 0) or pick **Table = 0**, **64 mm** or **128 mm** — at the steepest grade you pick: level at both ends, an eased start, constant grade and eased end, rounded to whole studs with the grade eased off to land exactly on the height. While its ghost points at a furniture surface it can reach ahead in the room (a ray from the open end along its heading meets the surface's entry, and the climb ends before it), one more chip offers that height, named by the furniture and surface (**KALLAX 5×5 · cubby floor ahead · +38 mm**). Before you place it, it shows the climb's length (ease + slope + ease) and whether it fits the room (green **fits**, amber **needs 3.4 m, room has ~1.9 m this way**); a ghost past a wall is red. Placed, it selects, moves, rotates and deletes as one piece; **Flip** turns a climb into a descent; its height and grade stay editable (**Climb · +38 mm · 1.2 m**), and the track after it follows its new end. **Level first** and **Level after** (0–512 mm) add level track before and after the slope, printed as part of the climb: laid on a turnout or crossing (or within 128 mm of level track of one) it starts with the level the points still need, shown on the ghost and in its options (**Level first: 128 mm (needed after points)**). It prints as wedges cut where the easements meet the slope and to the printer bed. |
| Flyover | Ramp up, 1–4 bridge decks and ramp back down, with the decks the chosen clearance (118 mm by default) above the rail tops of the track below. Click over the track to cross (the decks centre there) or on an open end. |

Checks flag grades over 4% (over 5% is an error), tight vertical curves, a level piece joined straight onto a slope, junctions on or next to a slope (the row names both pieces — **The climb starts right at the left turnout; points need 128 mm of level track before a slope.** — outlines both, and its one-click fix gives a Go up or down its missing **Level first**, or puts a printed level straight of the missing length between any other slope and the points, moving that side of the track along), and any crossing with less than 118 mm under it (with the height to raise it by). The legacy 6% **Ramp piece · 8 mm** tile (8 mm rise per piece) keeps its own checks and output.

The top view shows how high track is once any of it leaves the table: raised track is tinted warmer and brighter the higher it is, with a 0 → highest legend in the canvas corner; route ends, open ends and the foot and top of each slope are labelled (**+38 mm**); and a route's label gives its range (**Route 1 · 0–38 mm**) instead of **ground**. While Go up or down or a climb kit is armed, the 3D view labels each open end's height.

A selected piece's **Route height** (folded at the bottom of its panel) can **lift** the whole connected track by plates or bricks, and sets the **ground** under its route — the floor the whole route sits on: 0 is the table, a negative ground lets that line dip below the table top (for example into a lowered board), and every support stands on it. Furniture comes first: track resting on a surface (a KALLAX cubby floor or top, a table top, a shelf) needs no support there, and track raised above a surface stands on that surface, not the floor; past its edge (a gap between two pieces of furniture) supports go down to the ground again. Level track a whole number of plates above its ground, up to 96 mm, stands on printed **riser blocks** (4 × 8 studs, 1–10 plates tall, studs on top and stud sockets underneath, so they stack and sit on baseplates); stacks use 10-plate blocks plus one shorter block and sit under a full sleeper. Other raised track stands on columns; under a graded piece each column stops at that part's flat underside (graded parts print as wedges down to one flat underside, and the 3D view draws that wedge under the track with each column's seat plate on it). A column lower than its foot is a flat packer at the exact height; under a sloped underside that is not a wedge (the legacy Ramp piece · 8 mm) the column's seat tilts to the track's grade.

## Scenic pieces

| Tile | What prints |
| --- | --- |
| Buffer stop (32 or 64 mm) | One track connector and a stop block whose beam sits at coupler height (25.6 mm, 8 plates, above the baseplate). Its far end joins nothing and is not an open end. |
| Rerailer (64 or 128 mm) | A straight with ramps outside the rails up to rail height and bow-tie guides between them; works in both directions and never touches normal running. |
| Street track | Straight or R40–R120 curve with the road flush with the rail tops and 4 mm flangeway grooves (tram and street running). |
| Level crossing | Street track under a 60304 road plate (16 studs), square or 45° either way, plus loose road tiles beside it: an apron ramping down to the road plates, or, with **Next track**, half the filler to a parallel track 16 studs away. |

Plain printed track can also carry a **Colour marker** for the colour & distance sensor (88007) (white, red, yellow, green or blue). The marked sleeper gets a recess; the coloured insert prints on its own plate, labelled with its colour and preset to that filament colour in the 3MF, and presses in after printing.

See also the [print and build guide](docs/assembly/print-and-build.md), which ships inside every plates ZIP. Printed brackets have no load rating; have wall anchors and fasteners checked by someone qualified.

Every printed part has a short **code**: layout pieces are numbered in layout order (`1`, `2`, …), a piece printed as several parts gives each a letter (`1A`–`1I` for a turnout's parts, `2A`–`2J` for a climb's sections) and supports are `S1`, `S2`, …. The code names the part everywhere you meet it — the plate lists in Print, the object list of both 3MFs in your slicer, its STL file (`1A-left-turnout-base-1-of-5.stl`) and the guide; the layout's long ids stay in Layout data.

Every prepared package also carries a printable **Assembly guide (PDF)** (Print → downloads), drawn from the package's own meshes: a cover with the printer, style, date and totals (pieces, plates, print time, filament); a top-view layout overview with the room and furniture, your own track, detailed and fast printed track shaded by height, every piece's number and every support's square; the shopping list; one page per plate with its thumbnail, process, time, filament and parts by code; an exploded drawing, hardware and numbered steps for every multipart piece and mechanism, plus one page on joining plain printed track; the reference notes; and the physical-trial reminder and credits. The markdown guide stays alongside it as the source text. A layout prepared in parts has one guide for the whole layout, with a page listing each part's plates and pieces.

## Track plans (JSON)

A layout can also be described as a JSON **track plan** — tracks of steps such as "left turnout, four straights, 180° of R40, close back to the start" — and assembled by the same editor operations, then checked by fit and Test drive's traversal:

```sh
npm run plan -- docs/plans/examples/passing-loop.json [--out project.json] [--save]
```

It prints a report naming each problem by its plan step (`tracks[1].steps[3]`) with a fix, the open ends, which tracks the train can run, and the owned/printed bill. `--save` saves the project through the running service at `http://localhost:8766` so it appears under **Open**. The language, its report and five examples are in [docs/track-plan-language.md](docs/track-plan-language.md).

### Describe track (AI layout)

Build's **Describe track** button turns a sentence ("an oval in front of the KALLAX with a siding into a bottom cubby") into a track plan. Visitors and members alike use it on their own Anthropic API key: the browser asks Anthropic Claude for a plan directly (`src/plan/anthropic.ts`: a streamed `POST https://api.anthropic.com/v1/messages` with the `anthropic-dangerous-direct-browser-access` header; the system prompt is the language reference plus its examples, and the answer must fit [src/plan/plan.schema.json](src/plan/plan.schema.json)). Plateway's server never sees the key or the request. The browser builds the plan and sends the report back for up to three repair rounds, then shows it ghosted on the table with the model's notes and a compact report. **Accept** commits it as one undoable edit, even if problems remain (they are listed); **Discard** drops it; **Refine** changes it ("make the loop bigger"). "Start fresh" keeps the room, shelves, inventory and cars but replaces the track; "Add to my layout" builds onto the existing track through its open ends. The loop lives in `src/plan/assist.ts`.

The panel asks for the key the first time and keeps it in `sessionStorage`, or in `localStorage` with **Remember on this device**; it then shows "Using your key ending …abcd" with **Change key** and **Forget key**. A key Anthropic rejects (401) is forgotten and the panel asks again; signing out forgets it too. Before a run the panel says what a layout typically costs (about $0.19). The model (`claude-sonnet-5-5`) and effort (`medium`) are set in `src/plan/anthropic.ts`.

The system prompt's reference blocks and the `submit_plan` tool are generated into `src/plan/prompt.ts` from `docs/track-plan-language.md`, `docs/plans/examples/*.json` and `src/plan/plan.schema.json`; `npm run build` regenerates it, and after changing any of those run:

```sh
npm run plan-prompt
```

The eval runs 20 realistic requests ([docs/plans/eval/cases.json](docs/plans/eval/cases.json)) through the same loop and client with a key from the environment, scores each case's checks on the built layout, prints a table and writes `/tmp/plan-eval/<timestamp>.json` with every plan and report. `ANTHROPIC_MODEL` and `ANTHROPIC_EFFORT` (`low`…`max`) override the app's model and effort:

```sh
ANTHROPIC_API_KEY="$(op read 'op://<vault>/<item>/credential')" npm run plan-eval -- [--only simple-oval,helix] [--concurrency 3]
```

## Local data and clean handoff

- `.projects/plateway.db` (or `PLATEWAY_DB`) holds accounts, their projects (one row per saved revision), package receipts and calibration results. `.projects/exports/` is where the worker builds packages (and keeps a layout's part packages until they are combined); `.projects/storage/` holds the prepared packages, deleted 7 days after they were prepared. Saves from before accounts (`.projects/<id>-<revision>.json`) and calibration results in `.projects/calibrations/` import into one account with `uv run python scripts/import-local-projects.py .projects --email you@example.com`; running it again imports only what is new, and it never changes the local files. Packages prepared before storage stay in `.projects/exports/` but are no longer listed; prepare them again.
- `.projects/exports-cache/` and `.projects/calibrations/` are no longer used once imported; they are safe to delete.
- `.projects/` and `.learnings/` are ignored by git. Individual experiments, observations and calibration results are not built-in product defaults. Historical generated guides remain inside their original receipts.
- `TRAIN_PROJECT_DIR` selects a different local workspace. `TRAIN_EXPORT_DIR`, if explicitly set, selects a separate export root; unset it when testing an isolated workspace.
- A clean runtime handoff needs source, locked dependencies, bundled CAD reference/profile assets and assembly guides—not personal `.projects`, `.learnings`, historical planning notes, caches or an existing virtual environment. Install dependencies and build locally, then start with an empty data directory. Bambu Studio and its profiles remain explicit machine prerequisites.
- Increment the connector/profile version when its mating geometry or rail contract changes, and the calibration-process version when calibration production conditions change. Do not silently reuse old fit reports for a changed interface.
